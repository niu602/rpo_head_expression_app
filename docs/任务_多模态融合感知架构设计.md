# RPO 机器人多模态融合感知架构设计

> **项目**：RpoRobotExpression  
> **目标硬件**：红米 Note 12 Turbo（骁龙7+ Gen2，Android 13+）  
> **现状**：视觉（VisionManager）、语音（AsrManager/KwsManager）、IMU（ImuManager）三条管线完全独立运行，各自直接驱动表情/电机，没有信息融合层  
> **目标**：构建 `PerceptionFusionManager`，将人脸检测、表情识别、语音识别、IMU 姿态统一为时间对齐的事件流，送给 LLM 做综合判断

## 1. 整体架构

### 1.1 现状架构（独立管线）

```
摄像头 ──→ VisionManager ──→ ExpressionManager (表情镜像)
                              HeadControlManager (电机跟随)
                              
麦克风 ──→ KwsManager ──→ AudioManager ──→ 唤醒
         AsrManager ──→ LlmManager ──→ TtsManager (对话)
         
IMU    ──→ ImuManager ──→ HeadControlManager (点头/摇头检测)

触摸   ──→ PerceptionEventManager ──→ HeadControlManager
```

**问题**：
- 各传感器完全独立，无法综合判断
- 每条管线各自做简单判断（如"微笑→HAPPY"），无法理解复合信号
- 冲突场景无处理机制（皱眉+说"好"→ 到底是同意还是不满？）

### 1.3 PerceptionFusionManager 职责与接口

#### 职责定义

| 职责 | 说明 |
|---|---|
| **事件收集** | 接收所有感知源的标准化事件，注入事件总线 |
| **时间对齐** | 将不同延迟的事件按真实发生时间对齐 |
| **滑动窗口** | 维护最近 N 秒的事件窗口，自动淘汰过期事件 |
| **融合推理** | 对窗口内事件做规则+权重融合，输出高阶语义判断 |
| **冲突仲裁** | 当多源信号矛盾时，按策略仲裁 |
| **LLM 上下文构建** | 将融合结果格式化为 LLM 可理解的自然语言/JSON |
| **事件订阅** | 允许其他模块订阅融合结果（如 ModuleStateManager） |

#### 接口设计

```
// ===== 核心接口 =====

PerceptionFusionManager
│
├── // === 事件注入（各 Manager 调用） ===
├── fun emit(event: PerceptionEvent)
│
├── // === 查询 ===
├── fun getCurrentWindow(): List<PerceptionEvent>      // 获取当前窗口内事件
├── fun getFusionResult(): FusionResult                 // 获取最新融合判断
├── fun getRecentFusionResults(durationMs): List<FusionResult>
│
├── // === 订阅 ===
├── fun subscribeFusion(listener: (FusionResult) -> Unit)
│
├── // === 生命周期 ===
├── fun start()
├── fun stop()
└── fun release()


// ===== 触发控制 =====
├── fun setFusionTriggerMode(mode: FusionTriggerMode)
│   // IMMEDIATE  → 每个重要事件立即触发融合
│   // BATCHED    → 固定间隔批量融合（省电）
│   // ON_DEMAND  → 仅在 LLM 请求时才融合
│
└── fun setWindowDuration(ms: Long)                    // 窗口大小默认 5000ms
```

### 1.4 统一事件格式定义

```
PerceptionEvent
│
├── id: String                    // UUID，全局唯一
├── timestamp: Long               // 事件发生的真实时间（System.currentTimeMillis）
├── source: EventSource           // 事件来源枚举
│   ├── VISION                    // 视觉
│   ├── VOICE                     // 语音
│   ├── IMU                       // IMU
│   ├── TOUCH                     // 触摸
│   └── SYSTEM                    // 系统状态
│
├── type: EventType               // 事件类型枚举（见下表）
├── confidence: Float             // [0.0, 1.0]，置信度
├── data: Map<String, Any>        // 类型相关的负载数据
├── metadata: Map<String, String> // 辅助元数据
└── expireMs: Long                // 事件有效期（过期后从窗口移除）
```

| EventSource | EventType | data 字段 | 触发者 | 产生频率 |
|---|---|---|---|---|

| VISION | `FACE_EXPRESSION` | expression(SMILE/blink/surprise), probability | VisionManager | 10 Hz |

| VISION | `GESTURE_DETECTED` | gestureType(NOD_HEAD/SHAKE_HEAD/etc) | ImuManager/Vision | 离散 |
| VOICE | `SPEECH_DETECTED` | partialText | AsrManager | 实时 |
| VOICE | `SPEECH_COMPLETE` | fullText, language | AsrManager | 离散 |
| VOICE | `KEYWORD_DETECTED` | keyword, confidence | KwsManager | 离散 |
| VOICE | `EMOTION_FROM_VOICE` | emotion(HAPPY/ANGRY/SAD/CALM), confidence | ASR(可选) | 离散 |
| IMU | `HEAD_ACTION` | action(NOD/SHAKE/BOW/LOOK_UP), intensity | ImuManager | 离散 |
| IMU | `HEAD_POSE` | pitch, roll, yaw | ImuManager | 50 Hz |
| IMU | `MOTION_STATIC` | durationMs | ImuManager | 离散 |
| TOUCH | `TOUCH_EVENT` | x, y, action(PAT/TAP/LONG_PRESS) | PerceptionEventManager | 离散 |
| SYSTEM | `BATTERY_LOW` | level | BatteryManager | 离散 |

### 1.5 时间对齐策略

#### 问题

不同感知源有不同的处理延迟：

| 感知源 | 典型延迟 | 原因 |
|---|---|---|
| IMU | 5-20 ms | 传感器采样+滤波 |
| 视觉（ML Kit） | 30-60 ms | 相机曝光+ISP+ML Kit推理 |
| 语音 ASR | 500-2000 ms | 音频流式传输+云端识别延迟 |
| 关键词唤醒 | 200-500 ms | ASR fallback 延迟 |

同一条用户指令（如"摇头+说不"）的视觉事件和语音事件可能相差 1-2 秒到达。

#### 对齐策略：Timestamp Anchoring + Causal Window

**原则**：每个事件打上「真实发生时间」而非「到达时间」。

```
真实时间轴：
  t=0.0s   用户开始摇头
  t=0.3s   用户开始说"不对"
  t=0.5s   IMU检测到 SHAKE（延迟 20ms）
  t=0.8s   ML Kit检测到面部偏转（延迟 60ms）
  t=1.5s   ASR返回"不对"（延迟 ~1200ms）

对齐后窗口（以 t=1.5s 为锚点，向前看 3 秒）：
  ┌─────────────────────────────────┐
  │ t=0.5s  IMU: SHAKE (conf=0.9)   │
  │ t=0.8s  VISION: 面部偏转        │
  │ t=1.5s  VOICE: "不对"           │
  └─────────────────────────────────┘
  → 融合判断：用户在摇头+说不 = 强烈否定
```

**具体实现**：

1. **IMU 事件**：`timestamp = sensorEvent.timestamp` 转换为 epoch millis
2. **视觉事件**：`timestamp = ImageProxy.imageInfo.timestamp` 转换为 epoch millis  
3. **语音事件**：`timestamp = onSpeechStopped()` 时刻减去估计的说话时长  
4. **触摸事件**：`timestamp = System.currentTimeMillis()`（几乎无延迟）

**容差窗口**：时间对齐不需要精确到毫秒。融合引擎设置 **±500ms 容差**——在此范围内的事件视为"同时发生"。

### 1.6 滑动窗口机制

```
窗口设计：
  
  过期区          │◄──── 活跃窗口 (5000ms) ────►│
  
  ───────────────┼─────────────────────────────┼──────────
                  ↑                             ↑
              windowStart                  windowEnd (= now)
  
  规则：
  1. 窗口大小默认 5000ms，可根据场景调整
  2. 每 200ms 扫描一次，清除 expireMs 已过期的事件
  3. 重要事件（SPEECH_COMPLETE / KEYWORD_DETECTED）保留更久（expireMs=10s）
  4. 高频事件（FACE_DETECTED / HEAD_POSE）只保留最新 3 条
  5. 当窗口内事件数超过 50 条时，按优先级淘汰（低置信度先淘汰）

事件优先级：
  CRITICAL  > HIGH > NORMAL > LOW
  
  CRITICAL: SPEECH_COMPLETE, KEYWORD_DETECTED, FACE_RECOGNIZED
  HIGH:     FACE_EXPRESSION, HEAD_ACTION, GESTURE_DETECTED
  NORMAL:   FACE_DETECTED, SPEECH_DETECTED
  LOW:      HEAD_POSE, BATTERY_LOW
```

**窗口大小选择的理由**：
- 太短（< 2s）：跨模态事件来不及对齐就被丢弃
- 太长（> 10s）：窗口事件过多，LLM 上下文冗余
- 5s 是一条完整语音交互（说一句话 + 表情反应）的典型时长

## 2. 多源数据融合策略

### 2.1 融合引擎架构

```
           事件窗口
              │
    ┌─────────┼─────────┐
    ▼         ▼         ▼
┌────────┐┌────────┐┌────────┐
│规则引擎 ││权重融合 ││冲突仲裁 │
│RuleEng ││Weight  ││Conflict│
└────┬───┘└───┬───┘└───┬───┘
     │        │         │
     └────────┼─────────┘
              ▼
     ┌────────────────┐
     │ FusionResult   │
     │ (融合判断结果)  │
     └────────────────┘
```

### 2.2 规则引擎：Pattern-Based 融合

规则引擎定义「事件模式 → 语义标签」的映射规则。

#### 规则定义格式

```
Rule {
  name: String                    // 规则名称
  condition: EventPattern         // 事件匹配模式
  output: FusionJudgment          // 输出判断
  priority: Int                   // 规则优先级
}
```

#### 预定义规则集

| 规则名 | 条件模式 | 输出判断 | 优先级 |
|---|---|---|---|
| `STRONG_DISAGREE` | SHAKE + SPEECH("不"/"不对"/"错了") | `DISAGREE(strong=true)` | 100 |
| `STRONG_AGREE` | NOD + SPEECH("对"/"好的"/"嗯") | `AGREE(strong=true)` | 100 |
| `RELUCTANT_AGREE` | SHAKE + SPEECH("行吧"/"好吧"/"随便") | `RELUCTANT` (口是心非) | 90 |
| `GENUINE_AGREE` | NOD + SMILE | `AGREE(genuine=true)` | 90 |
| `CONFUSED_USER` | FROWN + SPEECH("什么"/"不懂"/"没听清") | `CONFUSION` | 85 |
| `ANGER_RISING` | FROWN + VOICE_TONE(angry) + VOLUME_HIGH | `ANGER(escalating=true)` | 95 |
| `HAPPY_INTERACTION` | SMILE + multiple_faces + SPEECH(any) | `JOYFUL_ENCOUNTER` | 80 |
| `USER_LEAVING` | FACE_LOST > 3s + no_speech > 5s | `USER_ABSENT` | 70 |
| `USER_APPROACHING` | FACE_DETECTED after FACE_LOST | `USER_RETURN` | 75 |
| `PAT_RESPONSE` | TOUCH(pat) + no_speech | `COMFORT_SEEKING` | 70 |

#### 事件模式匹配

```
EventPattern {
  requiredEvents: List<EventMatcher>   // 必须全部匹配
  withinMs: Long                        // 时间窗口约束
  minConfidence: Float                  // 最低综合置信度
}

EventMatcher {
  source: EventSource?
  type: EventType?
  dataPredicate: (Map<String,Any>) -> Boolean  // 负载数据匹配
}
```

**示例**：`STRONG_DISAGREE` 规则的模式定义

```
EventPattern {
  requiredEvents: [
    EventMatcher {
      source: IMU,
      type: HEAD_ACTION,
      dataPredicate: { it["action"] == "SHAKE" }
    },
    EventMatcher {
      source: VOICE,
      type: SPEECH_COMPLETE,
      dataPredicate: { textContains(it["fullText"], listOf("不","不对","错了","不是")) }
    }
  ],
  withinMs: 3000,   // 两个事件在 3 秒内
  minConfidence: 0.6
}
```

### 2.3 权重融合

不是所有事件组合都能命中预定义规则。权重融合处理 **一般性多源信号合并**。

#### 置信度加权

```
最终置信度 = Σ(事件置信度 × 来源权重) / Σ(来源权重)

来源权重：
  VOICE (SPEECH_COMPLETE):   1.0   ← 语音是最明确的意图信号
  VOICE (KEYWORD_DETECTED):   0.8
  VISION (FACE_EXPRESSION):  0.6   ← 表情有歧义
  VISION (FACE_RECOGNIZED):  0.9
  IMU (HEAD_ACTION):         0.7   ← 动作意图比较明确
  IMU (HEAD_POSE):           0.3   ← 连续姿态信息量低
  TOUCH:                      0.8
```

#### 情感维度映射

将多源事件映射到二维情感空间（Valence-Arousal 模型）：

```
                    高唤醒 (Arousal +)
                         │
           惊讶          │          生气
        (surprised)      │       (angry)
                          │
  负面 ─────────────────────────────────── 正面
  (Valence -)          │          (Valence +)
           悲伤          │           开心
        (sad)           │        (happy)
                          │
                    低唤醒 (Arousal -)

每个事件贡献一个向量：
  SMILE          → V=+0.6, A=+0.2
  FROWN          → V=-0.4, A=+0.3
  NOD            → V=+0.3, A=+0.1
  SHAKE          → V=-0.5, A=+0.2
  SPEECH("不对")  → V=-0.7, A=+0.4
  SPEECH("好的")  → V=+0.6, A=+0.1
  VOICE_TONE(angry) → V=-0.5, A=+0.6
  PAT            → V=+0.2, A=-0.1

融合时所有向量加权求和，得到最终情感坐标：
  finalV = Σ(event.V × confidence × weight) / normalization
  finalA = Σ(event.A × confidence × weight) / normalization

  → finalV < -0.3 && finalA > 0.3 → 负面高唤醒 → 可能生气/不满
  → finalV > 0.3 && finalA < 0.2 → 正面低唤醒 → 满意/开心
```

### 2.4 低置信度事件处理

| 置信度范围 | 处理策略 |
|---|---|
| `conf ≥ 0.8` | 直接采信，参与融合推理 |
| `0.5 ≤ conf < 0.8` | 参与融合，但权重降为正常的 50% |
| `0.3 ≤ conf < 0.5` | 不参与规则引擎匹配，仅作为弱信号在 LLM 上下文中标注为"不确定" |
| `conf < 0.3` | 丢弃，不进入窗口 |

**补充策略**：低置信度事件如果与高置信度事件 **同一来源连续出现 ≥ 3 次**，提升为中等置信度（时间一致性增强）。

```
示例：
  帧第1次: FROWN(conf=0.4)  → 弱信号
  帧第2次: FROWN(conf=0.45) → 弱信号
  帧第3次: FROWN(conf=0.42) → 弱信号
  → 连续3帧一致 → 提升为 conf=0.6，参与融合
```

### 2.5 事件冲突解决

#### 冲突类型与仲裁策略

| 冲突场景 | 仲裁规则 | 示例 |
|---|---|---|
| **语音 vs 视觉情绪** | 语音内容优先级 > 表情（人说话的措辞比微表情更可靠） | 皱眉+说"我很开心" → 信任语音，但标注"表情与语言不一致" |
| **语音 vs 动作** | 动作+语音一致 → 强化；动作+语音矛盾 → 标注矛盾，交给 LLM | 摇头+说"行吧" → 生成 RELUCTANT 标签 |
| **多视觉信号冲突** | 取置信度最高的信号，其他作为 context | 同时检测到微笑+惊讶 → 取 conf 高的 |
| **时序冲突** | 最新事件优先，旧事件衰减 | 3秒前开心，现在皱眉 → 当前状态=不满 |
| **来源可信度差异** | 权重高的来源主导 | ASR(0.9) vs 表情概率(0.5) → ASR 主导 |

#### 冲突仲裁算法

```
ConflictResolver:

  1. 检测冲突：同一时间窗口内存在 Valence 方向相反的事件
  
     if (events contain both V>0 and V<0 signals):
       → 触发冲突仲裁

  2. 仲裁步骤：
     a. 按来源权重排序
     b. 最高权重来源的信号方向为主判断
     c. 反方向信号作为"不一致标注"附加上下文
     d. 生成 FusionResult.conflictFlag = true
     
  3. 冲突标签：
     SPEECH_VS_EXPRESSION  → "说的话和表情不一致"
     SPEECH_VS_ACTION      → "说的话和动作不一致"
     EXPRESSION_VS_ACTION  → "表情和动作不一致"

  4. 冲突结果传递给 LLM 时：
     不做最终裁决，而是将冲突信息完整传递，
     让 LLM 结合对话历史和常识做判断
```

## 3. 示例场景设计

### 场景 1：皱眉 + 说了"不对" → 不满与道歉

## 4. 与 LLM 的交互方式

### 4.1 事件流到 LLM 的传递策略

#### 方案选择：增量+快照混合模式

| 策略 | 描述 | 适用场景 |
|---|---|---|
| **全量快照** | 每次对话请求都附带完整窗口快照 | LLM 需要完整上下文时 |
| **增量推送** | 只推送融合判断变化时的新增信息 | 省带宽/省 token |
| **混合模式（推荐）** | 每次对话附带「最近一条融合判断 + 摘要」 | 平衡信息量和 token 成本 |

**推荐方案细节**：

```
每次 LLM 请求时，在 system prompt 后追加 [感知上下文] 段落：

┌─────────────────────────────────────────────────┐
│ [感知上下文]                                      │
│                                                  │
│ 当前环境：1 人在场，注意力集中                     │
│ 用户状态：情绪正面(0.6)，唤醒度中等(0.3)           │
│ 最近动作：微笑(0.8, 2秒前)                        │
│ 最近语音：无                                      │
│ 冲突信号：无                                      │
│                                                  │
│ 历史融合(最近30秒)：                              │
│  - 5秒前: 点头同意 (AGREE, conf=0.85)             │
│  - 12秒前: 用户走近 (USER_RETURN)                 │
│                                                  │
│ ⚠ 注意：用户刚才微笑并点头，对上一轮对话表示满意   │
└─────────────────────────────────────────────────┘
```

### 4.2 System Prompt 增强设计

在现有 LlmManager 的 `DEFAULT_SYSTEM_PROMPT` 基础上，追加感知能力段落：

```
你是「小R」，一个可爱的桌面陪伴机器人。

【身份设定】
（... 保持原有 ...）

【感知能力】
你拥有以下感知通道，系统会在每次对话前为你提供 [感知上下文]：

1. 视觉感知：你能看到用户的面部表情（微笑、皱眉、惊讶等），
   知道有多少人在你面前，以及用户是否在看着你。
2. 听觉感知：你能听到用户说的话，感知语调和音量。
3. 姿态感知：你能感知用户的头部动作（点头、摇头、低头等）。
4. 触觉感知：你能感受到被触摸（拍头、轻触等）。

【感知信息使用规则】
1. 感知上下文中的信息是你的"感官"，自然地使用它们，不要生硬地复述。
   - ✅ "嘿嘿，看到你笑我也开心！" ← 自然
   - ❌ "检测到你的微笑概率为0.85" ← 机械
2. 当感知信息与用户的话语矛盾时，相信你的直觉，温柔地指出：
   - 用户说"没事"但皱着眉 → "真的没事吗？我看你好像不太开心……"
3. 当没有感知上下文或置信度很低时，不要编造感知信息。
4. 你可以主动利用感知信息发起话题（如"你刚才点头了，是同意我说的吗？"）。
5. 多人场景下要注意公平，不要只关注一个人。

【感知-行动映射建议】
- 用户开心 → 你也开心，可以更活泼
- 用户困惑 → 放慢语速，更耐心地解释
- 用户不满/生气 → 先道歉，然后调整方案
- 用户分心 → 用可爱的方式拉回注意力
- 用户悲伤 → 安慰，降低活泼度
- 用户离开 → 安静等待，省电模式
```

### 4.3 Token 成本控制

| 信息类型 | 估计 Token 数 | 频率 |
|---|---|---|
| 完整感知上下文段落 | ~150-200 tokens | 每次对话请求 |
| 历史融合摘要 | ~50-80 tokens | 每次对话请求 |
| 冲突标注 | ~20-30 tokens | 仅冲突时 |
| **总计增量** | **~200-300 tokens/轮** | — |

> 当前 MAX_CONTEXT_TOKENS = 8000（含对话历史），感知上下文约占 3-4%，完全可接受。

**优化策略**：
- 当连续 3 轮对话的感知状态未变化时，压缩为"（感知状态无变化：正面/注意力集中）"，节省 token
- 低置信度事件不传给 LLM，只在融合层消化
- 历史摘要按时间衰减，10 秒前的事件只保留标签不留细节

### 4.4 LLM 请求时机

```
触发 LLM 请求的条件（任一满足）：

1. 用户语音输入完成（现有行为）
   → 常规对话流程 + 附带感知上下文

2. 融合判断发生重大变化（无需用户说话）
   → 如检测到 USER_DISTRESS / USER_DISTRACTED
   → 主动发起对话（"你还好吗？" / "诶你在看什么？"）
   → 限制频率：同类主动对话 30 秒内不重复

3. 关键事件触发
   → FACE_RECOGNIZED: 主动打招呼
   → 多人聚集: 主动欢迎
   → 触摸互动: 回应（已有行为）
```

## 5. 性能和复杂度评估

### 5.1 计算复杂度

| 组件 | 时间复杂度 | 空间复杂度 | 实际开销 |
|---|---|---|---|
| 事件总线（插入/删除） | O(1) / O(n) | O(n), n=窗口事件数 | <0.1ms / 事件 |
| 窗口清理（200ms周期） | O(n) | — | n≤50, <0.5ms |
| 规则引擎匹配 | O(R × E), R=规则数, E=事件数 | — | R≈15, E≈20, <1ms |
| 权重融合（V-A 计算） | O(E) | — | <0.1ms |
| 冲突检测 | O(E²) | — | E≤20, <0.5ms |
| LLM 上下文构建 | O(E) | — | <0.5ms |
| **单次融合总耗时** | — | — | **< 3ms** |

> 融合引擎的计算开销极小（< 3ms），完全不会成为性能瓶颈。

### 5.2 内存占用

| 组件 | 内存占用 |
|---|---|
| 事件窗口（50 条事件） | ~50KB |
| 融合规则集（15 条） | ~5KB |
| 历史融合结果（100 条） | ~20KB |
| V-A 情感模型状态 | <1KB |
| **总计** | **~80KB** |

### 5.3 CPU 影响评估

| 运行模式 | 融合频率 | CPU 占用 |
|---|---|---|
| IMMEDIATE（每个事件触发） | ~30 Hz (视觉高频) | 1-2% |
| BATCHED（200ms 周期） | 5 Hz | <0.5% |
| ON_DEMAND（仅 LLM 请求时） | <0.1 Hz | <0.1% |

**推荐**：日常使用 `BATCHED` 模式（200ms 周期），对话时切换到 `IMMEDIATE` 模式以获得最佳响应性。

### 5.4 延迟影响

| 环节 | 延迟 |
|---|---|
| 事件注入到事件总线 | < 1ms |
| 融合引擎处理 | < 3ms |
| LLM 上下文构建 | < 1ms |
| LLM 请求增加的 Token 解析时间 | ~10-30ms（多 200 tokens） |
| **对用户可感知延迟的影响** | **< 50ms（不可感知）** |

### 5.5 与现有管线的兼容性

```
关键原则：PerceptionFusionManager 是「旁路监听」模式，
不阻断现有管线的直接响应路径。

现有快速响应路径（不变）：
  FACE_EXPRESSION → ExpressionManager (镜像，< 16ms)
  HEAD_POSE → HeadControlManager (跟随，< 30ms)
  KEYWORD → AudioManager (唤醒，立即)

新增融合路径（旁路）：
  所有事件 → PerceptionEventBus → FusionManager → LLM
  （异步、延迟容忍、不阻断快速路径）
```

| 现有模块 | 变更类型 | 影响 |
|---|---|---|
| VisionManager | 增加 `emit()` 调用（1行代码/事件） | 无性能影响 |
| AsrManager | 增加 `emit()` 调用 | 无性能影响 |
| ImuManager | 增加 `emit()` 调用 | 无性能影响 |
| PerceptionEventManager | 增加 `emit()` 调用 | 无性能影响 |
| LlmManager | `sendQuery()` 前调用 `getFusionContext()` | 增加 ~200 tokens |
| ExpressionManager | 订阅融合结果，用于增强表情选择 | 可选增强 |
| ModuleStateManager | 作为融合结果的消费者 | 可选增强 |

### 6.3 与 ModuleStateManager 的关系

```
现有：ModuleStateManager 是「状态→表情」的简单映射
      onAsrStartListening → RECOGNIZING 表情

未来：PerceptionFusionManager 是「多源融合→综合判断」
      ModuleStateManager 成为融合结果的消费者之一

         PerceptionFusionManager
                  │
          ┌───────┼───────────────┐
          ▼                       ▼
  ModuleStateManager        LlmManager
```

**过渡策略**：
- Phase 1-2 中 ModuleStateManager 保持不变，PerceptionFusionManager 并行运行

- 最终 ModuleStateManager 退化为融合结果的执行器

## 附录 C：与 PerceptionEventManager 的关系

现有 `PerceptionEventManager` 是触摸/人脸/IMU 事件通过 Protobuf 编码发送到板端的通信层。

`PerceptionFusionManager` 是概念上不同的层：

```
PerceptionEventManager (现有)：
  职责：将感知事件编码为 Protobuf → 通过 MultiLinkManager 发到板端
  方向：Phone → 硬件板（通信层）

PerceptionFusionManager (新增)：
  职责：将感知事件融合为高阶语义判断 → 送给 LLM
  方向：传感器 → 融合 → LLM（智能层）
```

两者并行运行，互不干扰：
- PerceptionEventManager 继续负责硬件通信（低级事件转发）
- PerceptionFusionManager 负责智能融合（高级语义判断）
- 两者订阅同一批 Manager 的回调，各自独立处理
