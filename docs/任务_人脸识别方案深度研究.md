### 1.2 方案详细评估

#### ① MobileFaceNet + TFLite ★★★★★（首选）

**技术概述**  
MobileFaceNet 由 Yu Chen 等人于 2018 年提出，专为移动端人脸识别设计。采用 Depthwise Separable Convolution + Linear Bottleneck 结构，全局平均池化后接 1×1 卷积输出嵌入向量。训练时使用 ArcFace Loss（也称 ArcMargin），在 LFW 上达到 99.50% 准确率。

**优势**：
- 模型极小（量化后 < 5MB），不增加 APK 体积压力
- 推理速度极快（中端机 8～15ms），完全满足实时需求
- TFLite 生态完善，官方有 `FaceMesh` + 自定义模型组合方案
- Google 持续优化 Delegate（NNAPI / GPU），未来可零成本提速
- 模型文件可直接嵌入 assets 目录，无需后端

**劣势**：
- 在极端光照/大角度偏转（>45° yaw）时准确率下降
- 需要自己做预处理（检测→对齐→裁剪→归一化）

**社区资源**：
- 预训练模型：TensorFlow Lite Examples 官方 `face_mesh` + `face_contour` → 自训 MobileFaceNet
- 开源实现：`takuoshihiro/mobilefacenet-tfjs`、`peteryuX/face-recognition-using-mobilefacenet`
- 多个量化 .tflite 模型可直接下载使用

#### ② FaceNet (Inception-ResNet-v1) + TFLite ★★★☆☆

**技术概述**  
Google 2015 年提出，使用 Inception-ResNet 作为 backbone， triplet loss 训练，输出 512 维嵌入。LFW 99.63%+。

**优势**：
- 经典方案，文献丰富，预训练模型易获取
- 嵌入质量高，泛化能力强

**劣势**：
- **模型巨大**（22MB int8 / 92MB float32），对移动端不友好
- 推理慢（30～80ms），与现有 30fps 相机管线冲突
- 内存占用高，红米 Note 12 Turbo 上跑 ML Kit + FaceNet 会逼近 300MB

**结论**：作为学术对比参考，**不推荐生产部署**。

#### ③ ArcFace (ResNet-100) + NCNN ★★☆☆☆

**技术概述**  
InsightFace 团队提出的 ArcFace Loss + ResNet-100/50 backbone。在 LFW/CFP/IJB-C 上 SOTA 级别准确率。NCNN 是腾讯开源的神经网络推理框架，针对 ARM 做了极致优化。

**优势**：
- 准确率天花板（LFW 99.83%+）
- NCNN 在 ARM CPU 上速度优秀，支持 Vulkan GPU
- 无 NDK/TFLite 依赖

**劣势**：
- **集成复杂度最高**：需要编译 NCNN 静态库、写 JNI C++ 层、管理模型加载
- ResNet-100 模型 250MB，ResNet-50 也有 166MB，即使量化后仍有 17～64MB
- 与现有 TFLite/Kotlin 生态割裂
- APK 体积暴增

**结论**：准确率最高但工程代价过大，**不符合本项目的快速迭代节奏**。

#### ④ ArcFace (MobileFaceNet/ResNet-18) + MNN ★★★☆☆

**技术概述**  
阿里 MNN（Mobile Neural Network）框架 + 轻量 ArcFace 模型。MNN 在 ARM 上性能与 NCNN 接近，但有官方 Java/Kotlin API。

**优势**：
- 比 NCNN 更好的 Android Java 支持
- 可以用 MobileFaceNet backbone（4MB）跑 ArcFace loss
- 支持 int8 量化，推理速度快

**劣势**：
- 需引入 MNN 运行时（~3MB native lib）
- 社区生态不如 TFLite
- 模型转换链（PyTorch → ONNX → MNN）有学习成本

**结论**：性能与 TFLite 方案接近，但生态优势不足。**作为备选方案保留**。

#### ⑤ ML Kit 旧版 Face Identification 替代 ★☆☆☆☆

Google 曾在 Firebase ML Kit 中提供人脸识别 API，但已弃用。当前 ML Kit face-detection（`com.google.mlkit:face-detection`）**只支持检测（Detection），不支持识别（Recognition）**。Google 官方推荐自行集成 TFLite 模型。

**结论**：**无现成 API 可用**，必须自建识别链路。

### 1.3 对比结论

```
推荐排序：
  ① MobileFaceNet + TFLite     → ★★★★★  首选（体积/速度/准确率/集成难度最优平衡）
  ④ ArcFace-MobileFace + MNN   → ★★★☆☆  备选（若未来需要更高准确率）
  ② FaceNet + TFLite           → ★★★☆☆  不推荐（模型过大）
  ③ ArcFace-R100 + NCNN        → ★★☆☆☆  不推荐（集成复杂度过高）
  ⑤ ML Kit 识别                 → ★☆☆☆☆  无此功能
```

## 2. 推荐方案与详细设计

### 2.1 模型选择

| 项目 | 选择 | 理由 |
|---|---|---|
| **Backbone** | MobileFaceNet | 专为移动端设计，Depthwise Separable Conv 算力需求极低 |
| **输入尺寸** | 112×112×3 (RGB) | ArcFace 标准输入，平衡精度与速度 |
| **输出维度** | 192 维 | 比 128 维泛化更好，比 512 维省存储/计算 |
| **量化方式** | **Full INT8 量化** | 模型从 ~4.2MB 压缩到 **~1.8MB**，推理速度提升 2-3x，精度损失 < 0.3% |
| **归一化** | 像素值 / 255.0 → [-1, 1] 线性映射 | 标准做法 |
| **损失函数（训练时）** | ArcFace Loss (margin=0.5, scale=64) | 业界公认最优的度量学习损失 |

**推荐预训练模型来源**：
```
peteryuX/face-recognition-using-mobilefacenet
  → mobile_face_net.tflite (INT8, 192-dim, ~1.8MB)
  → LFW accuracy: 99.50%
```

或使用 InsightFace 官方预训练权重自行转换：
```
InsightFace MobileFaceNet (ArcFace trained)
  → PyTorch → ONNX → TFLite (int8 quantization)
```

### 2.2 部署框架：TFLite

**选择 TFLite 而非 NCNN/MNN 的理由**：

| 对比项 | TFLite | NCNN | MNN |
|---|---|---|---|
| **Android 集成** | Gradle 一行依赖 | 需编译 .so + JNI | 需引入 .so + wrapper |
| **Kotlin API** | 原生支持 | 仅 C++/Java JNI | Java wrapper |
| **Delegate 生态** | NNAPI / GPU / CoreML | Vulkan | Vulkan / OpenCL |
| **调试工具** | TFLite Profiler / Benchmark | 有限 | 有限 |
| **与现有项目一致性** | 项目已用 ML Kit（Google 生态） | 需引入全新依赖 | 需引入全新依赖 |
| **APK 增量** | ~2MB (tflite-runtime) | ~4MB (ncnn + opencv) | ~3MB (mnn) |

**集成方式**：
```
// build.gradle.kts 新增
implementation("org.tensorflow:tensorflow-lite:2.16.1")
implementation("org.tensorflow:tensorflow-lite-support:0.4.4")
implementation("org.tensorflow:tensorflow-lite-gpu:2.16.1")  // GPU Delegate（可选）
```

模型文件放置在 `app/src/main/assets/models/mobile_face_net.tflite`。

### 2.3 人脸对齐方案

人脸对齐（Face Alignment）是准确率的关键。未对齐的人脸会显著降低识别精度。

#### 对齐流程

```
原始帧 → ML Kit 检测 → 提取 5 关键点 → 仿射变换对齐 → 112×112 裁剪
```

#### 关键点来源

**利用现有 ML Kit Face Detection**（已集成，零额外依赖）：

ML Kit 的 `Face` 对象提供以下关键点（`FaceLandmark`）：

| 关键点 | ML Kit 枚举 | 用途 |
|---|---|---|
| 左眼中心 | `LEFT_EYE` | 仿射变换参考点 |
| 右眼中心 | `RIGHT_EYE` | 仿射变换参考点 |
| 鼻尖 | `NOSE_BASE` | 仿射变换参考点 |
| 左嘴角 | `LEFT_MOUTH` | 仿射变换参考点 |
| 右嘴角 | `RIGHT_MOUTH` | 仿射变换参考点 |

> **注意**：ML Kit 关键点基于 2D 坐标，不含 Z 轴深度。对于 < 30° 偏转的人脸足够。大角度侧脸建议丢弃（不对齐也不识别）。

#### 仿射变换对齐

使用标准 ArcFace 5 点对齐模板：

```
标准模板坐标（112×112 图像空间）：
  左眼:   (38.29, 51.70)
  右眼:   (73.53, 51.50)
  鼻尖:   (56.02, 71.74)
  左嘴角: (41.54, 92.37)
  右嘴角: (70.73, 92.13)

计算步骤：
1. 从 ML Kit 获取 5 个关键点的实际坐标
2. 计算 5 个关键点从「实际位置」到「标准模板位置」的仿射变换矩阵 M
3. 对原始图像应用 cv2.warpAffine(M, dsize=(112,112))
4. 输出对齐后的 112×112 RGB 图像
```

**关键点缺失处理**：当 ML Kit 未检测到某个关键点（小脸/侧脸）时，跳过对齐直接裁剪人脸边界框，但标记 `isAligned=false`，降低匹配置信度权重。

#### 是否需要 OpenCV？

仿射变换矩阵的数学计算（3点法或最小二乘法）可以用纯 Kotlin 实现（~80行），不强制依赖 OpenCV。

**推荐方案**：先用纯 Kotlin 实现仿射变换（避免引入 OpenCV 增大 APK），若精度不足再引入 `org.opencv:opencv` 的 `Imgproc.warpAffine`。

### 2.4 相似度匹配算法

#### 度量选择：余弦相似度

```
cosine_similarity = (A · B) / (||A|| × ||B||)
```

**选余弦相似度而非欧氏距离的理由**：
- ArcFace Loss 训练的嵌入向量在超球面上优化，余弦相似度与训练目标一致
- 对嵌入向量的模长不敏感，鲁棒性更好
- 值域 [-1, 1]，阈值设定直观

#### 阈值选择

| 阈值 | FAR (误识率) | FRR (拒识率) | 含义 |
|---|---|---|---|
| 0.30 | ~10⁻¹ | ~10⁻³ | 宽松，几乎不漏识，但容易认错人 |
| 0.40 | ~10⁻² | ~10⁻² | **推荐阈值（家庭场景）** |
| 0.45 | ~10⁻³ | ~5×10⁻² | 平衡，适合一般场景 |
| 0.50 | ~10⁻⁴ | ~10⁻¹ | 严格，准确但可能漏识 |
| 0.55 | ~10⁻⁵ | ~2×10⁻¹ | 非常严格 |

> 以上阈值数据基于 MobileFaceNet (192-dim, ArcFace) 在 LFW/CALFW 上的 ROC 曲线推算。

**推荐阈值设计**：
```kotlin
// 分层阈值策略
val THRESHOLD_CONFIRMED = 0.50f   // 确认识别成功（高置信度，直接叫名字）
val THRESHOLD_TENTATIVE = 0.40f   // 猜测性识别（低置信度，「你是XX吗？」）
val THRESHOLD_UNKNOWN = 0.30f     // 低于此值视为陌生人
```

**策略说明**：
- `sim ≥ 0.50`：直接识别为已注册用户，触发对应欢迎表情/语音
- `0.40 ≤ sim < 0.50`：识别为可能是某人，以疑问句确认（"你是XX吗？"），用户确认后更新嵌入
- `sim < 0.40`：陌生人，如果用户说"我是XX"则进入注册流程

#### 嵌入向量存储

每个注册用户存储 **N 帧嵌入的平均值**（注册时采集多帧）：

```
用户 "小明":
  faceEmbedding: FloatArray(192)  // 多帧平均后的归一化向量
  embeddingHistory: List<FloatArray> // 保留原始帧用于增量更新
  registeredAt: Long
  lastSeen: Long
```

**增量更新**：每次成功识别后，如果相似度 > 0.55，将该帧嵌入以指数加权方式融入存储向量：
```
storedEmbedding = α × storedEmbedding + (1-α) × newEmbedding    // α = 0.9
```

这样用户的嵌入向量会随时间微调适应轻微外观变化（戴眼镜、发型变化等）。

## 3. 注册流程设计

### 3.1 完整注册流程

```
用户说 "我叫小明"
    │
    ▼
┌──────────────────────┐
│ ASR 识别到 "我叫XX"   │
│ NLP 提取姓名 "小明"   │
└──────────┬───────────┘
           │
           ▼
┌──────────────────────┐
│ 检查是否已注册 "小明"  │
│  - 是 → "你已经注册过啦~"
│  - 否 → 进入注册流程   │
└──────────┬───────────┘
           │
           ▼
┌──────────────────────────────────┐
│ TTS: "小明你好呀！看着我，我要记住你啦~" │
│ ExpressionManager → HAPPY         │
│ 提示用户正对摄像头                 │
└──────────┬───────────────────────┘
           │
           ▼
┌──────────────────────────────────┐
│         采集阶段（3秒）            │
│                                   │
│ 条件：ML Kit 检测到 1 张人脸        │
│       人脸偏转角 < 20°             │
│       人脸占屏比 > 0.10            │
│       有全部 5 个关键点             │
│                                   │
│ 每 200ms 采集 1 帧（共 ~15 帧）     │
│ 对每帧做对齐 → MobileFaceNet 推理   │
│ 存入候选嵌入列表                    │
└──────────┬───────────────────────┘
           │
           ▼
┌──────────────────────────────────┐
│         质量筛选                   │
│                                   │
│ 从 ~15 帧候选中：                   │
│ 1. 剔除模糊帧（Laplacian 方差 < τ） │
│ 2. 剔除偏转角 > 15° 的帧            │
│ 3. 按清晰度排序取 Top-5            │
│ 4. 检查 5 帧两两相似度均 > 0.6     │
│    （确保不是混合了多个人）          │
│ 5. 取 5 帧嵌入的平均值并 L2 归一化   │
└──────────┬───────────────────────┘
           │
           ▼
┌──────────────────────────────────┐
│ TTS: "记住你啦！下次见面我叫你~"     │
│ ExpressionManager → HAPPY + WINK  │
│ 保存到本地数据库                    │
└──────────────────────────────────┘
```

### 3.2 质量帧筛选标准

| 指标 | 阈值 | 实现 |
|---|---|---|
| 人脸检测置信度 | > 0.7 | ML Kit `face.trackingId != null && 所有关键点存在` |
| 人脸偏转角 (Euler Y) | < ±20° | ML Kit `face.eulerY` |
| 人脸偏转角 (Euler Z) | < ±15° | ML Kit `face.eulerZ` |
| 人脸占屏比 (宽/屏宽) | > 0.10 | 对应约 0.5m 距离 |
| 图像清晰度 | Laplacian 方差 > 100 | 纯 Kotlin Sobel/Laplacian 或跳过 |
| 关键点完整性 | 5/5 | ML Kit `FaceLandmark` 全部非 null |
| 光照检查 | 平均亮度 > 50 / < 220 | YUV → Y 通道均值 |

### 3.3 活体检测与防假

#### 威胁分析

| 攻击类型 | 风险等级 | 场景 | 是否需要防御 |
|---|---|---|---|
| 照片攻击 | ★★★☆☆ | 拿手机照片对着机器人 | **需要**（低成本攻击） |
| 视频回放 | ★★☆☆☆ | 播放视频欺骗 | 可选（桌面机器人场景概率低） |
| 3D 面具 | ★☆☆☆☆ | 高成本攻击 | 不需要（场景不需要金融级安全） |

#### 推荐活体检测策略：交互式活体（零额外模型）

**不做静默活体检测（Silent Liveness）**，而是利用机器人天然有交互能力的优势，设计 **配合式活体检测**：

```
注册时：
  TTS: "看着我哦，眨眨眼~"
  → ML Kit 检测到眨眼动作 → 通过
  
  TTS: "再笑一个~"
  → ML Kit 检测到微笑（smilingProbability > 0.7）→ 通过

日常识别时：
  不做活体检测（性能考虑），但增加以下隐式信号：
  1. 连续 3 帧嵌入一致（照片无法产生帧间微动）
  2. 检测到自然微动（瞳孔微动 / 眼睑微动 / 表情微变）
  3. 人脸不是完全静止的（利用 ML Kit trackingId 的帧间位移）
```

**优势**：
- 零额外模型，零额外算力
- 自然融入注册流程，用户体验好
- 照片攻击需要同时模拟眨眼+微笑，门槛足够高

**如果未来需要更强的活体检测**：
- 引入 TFLite `silero-vad` 检测唇动（语音 + 视觉唇动同步）
- 引入 MiniFASNet（~1MB，静默活体）作为可选增强

## 4. 性能预估

### 4.1 单帧推理耗时

**测试基准**：红米 Note 12 Turbo（骁龙 7+ Gen2，4×A715 + 4×A510，Adreno 725）

| 阶段 | 耗时 (CPU 4线程) | 耗时 (NNAPI Delegate) | 说明 |
|---|---|---|---|
| ML Kit 人脸检测 | 8～15 ms | — | 已在运行，不额外计算 |
| 关键点提取 | 0 ms | — | ML Kit 检测结果直接用 |
| 仿射变换对齐 | 1～3 ms | — | 纯 Kotlin/C，极快 |
| 图像预处理 (归一化) | 1～2 ms | — | 112×112 小图 |
| **MobileFaceNet 推理 (INT8)** | **8～15 ms** | **5～8 ms** | TFLite CPU / NNAPI |
| 嵌入后处理 (L2归一化) | < 1 ms | — | 192维向量运算 |
| **余弦相似度匹配 (N人)** | **0.1×N ms** | — | 矩阵点积 |
| **总耗时 (1人已注册)** | **~20～35 ms** | **~15～25 ms** | 含检测+对齐+推理+匹配 |
| **总耗时 (10人已注册)** | **~21～36 ms** | **~16～26 ms** | 匹配开销可忽略 |

> MobileFaceNet INT8 推理数据参考 TFLite benchmark 在骁龙 855（~6ms）和骁龙 660（~18ms）上的实测值，骁龙 7+ Gen2 性能介于两者之间，偏向 855。

### 4.2 内存占用

| 组件 | 内存增量 |
|---|---|
| TFLite 运行时 + 模型加载 | +8～12 MB |
| 推理中间张量 (Tensor arena) | +2～4 MB |
| 嵌入向量数据库 (100人) | < 0.1 MB (192 × 4B × 100 = 77KB) |
| 人脸对齐中间图像 | +0.5 MB (112×112×3) |
| **总计** | **+10～17 MB** |

现有 App 内存约 150～200MB（含 CameraX + ML Kit + Compose），增加人脸识别后总内存 **~170～215MB**，完全在红米 Note 12 Turbo（8/12GB RAM）的承受范围内。

### 4.3 多人同时识别性能

| 场景 | 人脸数 | 检测 | 推理 | 匹配 | 总耗时 | 帧率影响 |
|---|---|---|---|---|---|---|
| 单人 | 1 | 10ms | 12ms | 0.1ms | ~25ms | 无影响 (40fps headroom) |
| 双人 | 2 | 12ms | 24ms | 0.2ms | ~38ms | 无影响 (26fps) |
| 3-4 人 | 4 | 15ms | 48ms | 0.4ms | ~65ms | 轻微降帧 (15fps) |
| 5+ 人 | 6 | 18ms | 72ms | 0.6ms | ~93ms | **降帧** (11fps) |

**多人场景优化策略**：
- 3+ 人时降频为每 3 帧识别 1 次（与现有 VisionManager 多人模式一致）
- 利用 ML Kit `trackingId` 做帧间缓存，同一 trackingId 只在首次出现时推理，后续帧复用嵌入
- 人脸丢失后 500ms 内不清除缓存，减少重复推理

### 4.4 功耗影响

| 模式 | CPU 额外占用 | 电池影响 |
|---|---|---|
| 待机（无人在前） | 0% | 无 |
| 单人对话 | +15～25% | 可忽略（对话时间短） |
| 多人场景 | +30～40% | 建议降频 |

## 5. 风险与注意事项

### 5.1 技术风险

| 风险 | 等级 | 影响 | 缓解措施 |
|---|---|---|---|
| ML Kit 关键点不全（侧脸/小人脸） | 中 | 对齐失败→精度下降 | 关键点不全时降级为裁剪，标记低置信度 |
| 极端光照（逆光/暗光） | 中 | 嵌入质量差→误识 | 检查亮度，过暗/过亮时提示用户调整 |
| 模型在特定人群表现差异 | 低 | 儿童可能识别率低 | 注册时多采帧，增量学习 |
| TFLite 模型版本兼容 | 低 | 升级 TFLite 后推理失败 | 锁定 tflite 版本，CI 中跑模型测试 |
| 大角度偏转 | 中 | 无法识别 | > 30° 偏转时不识别，等待用户回正 |

### 5.2 隐私合规

| 事项 | 处理方式 |
|---|---|
| 人脸数据存储位置 | **仅本地**（Room/DataStore），不上传服务器 |
| 人脸图像存储 | **不存原始图像**，只存 192 维嵌入向量（不可逆） |
| 用户删除权 | 提供"忘记我"功能，删除指定用户全部数据 |
| 隐私声明 | 首次使用时弹出说明，用户同意后启用 |
| GDPR/个人信息保护法 | 嵌入向量属于个人信息，需遵循最小必要原则 |

### 5.3 工程注意

| 事项 | 说明 |
|---|---|
| TFLite 模型加载 | 使用 `Interpreter` + `MemoryArena` 优化，避免频繁创建/销毁 |
| 线程模型 | 推理在 `Dispatchers.Default` 上运行，不阻塞 UI 线程 |
| 模型热更新 | 模型放在 assets，如需更新随 APK 发布；不考虑运行时下载（安全性） |
| 与 VisionManager 协调 | 人脸检测复用 VisionManager 的 ML Kit 检测结果，不重复检测 |
| 数据库迁移 | 嵌入向量格式变更时需要 migration |

### 6.2 接口设计（概念定义，非实现）

```
FaceRecognitionManager
├── fun initialize()                                          // 加载 TFLite 模型
├── fun recognize(face: Face, image: InputImage): RecResult   // 识别单张人脸
├── fun recognizeAll(faces: List<Face>, image): List<RecResult> // 多人识别
├── fun startRegistration(name: String, callback)             // 开始注册
├── fun deleteUser(name: String)                              // 删除用户

```

### 6.3 与现有模块的联动

```
                    ┌─────────────────┐
                    │  VisionManager   │
                    │ (ML Kit 检测)    │
                    └────────┬────────┘
                             │ Face + InputImage
                             ▼
┌──────────────────────────────────────────────┐
│           FaceRecognitionManager              │
│  ┌──────────┐  ┌──────────┐  ┌────────────┐ │
│  │ Aligner  │→│ Embedder │→│ Database   │ │
│  │ (对齐)   │  │ (TFLite) │  │ (匹配存储) │ │
│  └──────────┘  └──────────┘  └─────┬──────┘ │
└────────────────────────────────────┼────────┘
                                     │ RecResult
                    ┌────────────────┼───────────────┐
                    ▼                ▼               ▼
          ┌──────────────┐  ┌──────────────┐ ┌─────────────┐
          │ModuleStateMgr│  │  TtsManager   │ │ExpressionMgr│
          │ (状态联动)    │  │ "小明你好呀~" │ │ → HAPPY     │
          └──────────────┘  └──────────────┘ └─────────────┘
```

**关键联动点**：

1. **VisionManager** → 在 `analyze()` 回调中，将 `Face` 对象和 `InputImage` 传给 `FaceRecognitionManager.recognize()`
2. **识别成功** → `ModuleStateManager.onFaceRecognized(name)` → `TtsManager.speak("小明你好呀~")` + `ExpressionManager.requestExpression(HAPPY)`
3. **注册流程** → ASR 识别到"我叫XX" → `FaceRecognitionManager.startRegistration("XX")` → 采集完成后 TTS 确认
4. **识别频率**：与 VisionManager 的帧率控制一致——单人每帧、多人每 3 帧、利用 trackingId 缓存

### 6.4 性能保护机制

- 识别任务优先级低于表情动画渲染，在 `Dispatchers.Default` 上运行
- 设置推理超时保护：单帧推理 > 50ms 时自动降级为每 5 帧识别一次
- 内存监控：可用内存 < 100MB 时暂停识别功能，释放 TFLite 模型
